### 0.1 Session persistence — fixed and verified `[BE]` ✅
`feedback.md` reports users logged out after ~10-15 min despite a documented 30-min inactivity window. Traced the cause:
- `SESSION_TIMEOUT_MS` (default 30 min) is checked identically in `api-gateway/middleware/auth.js`, root `middleware/auth.js`, and every service's `src/middleware/auth.js` — each does `inactiveTime = Date.now() - user.lastActivity` where `user` is the **decoded JWT payload**.
- The code then does `user.lastActivity = Date.now()` — but this mutates the in-memory decoded object only. **No new token is issued or sent back to the client.** The client keeps resending the original token from login, whose `lastActivity` claim never moves.
- Net effect: this is not a sliding inactivity window at all — it's a fixed timeout measured from login (or from the last token refresh, if refresh also doesn't bump `lastActivity` — needs confirming in `services/auth-service/src/utils/jwt.js`). Any client-side clock drift, multi-tab usage, or a shorter-than-expected refresh cadence would present exactly as "logged out after 10-15 min."

**Fix applied**: `lastActivity` is no longer trusted from the JWT claim. It's now tracked server-side in Redis (key `last_activity:<userId>`, TTL = `SESSION_TIMEOUT_MS`, refreshed on every authenticated request) in the 3 places that actually enforce this check on the live request path: `services/auth-service/src/utils/redisClient.js` + `api-gateway/utils/redisClient.js` (extended with `updateLastActivity`/`getLastActivity`), plus a new minimal `services/ninja-sales-service/src/utils/redisClient.js` (that service didn't have a Redis client at all before). The middlewares in `services/auth-service/src/middleware/auth.js`, `api-gateway/middleware/auth.js`, and `services/ninja-sales-service/src/middleware/auth.js` now check/refresh Redis instead of the static JWT claim, falling back to the token's `iat` only for the very first request after login/refresh (before Redis has a record). Root `middleware/auth.js` and `middleware/tokenBlacklist.js` turned out to be dead code — nothing actually requires them (every service has its own local copy) — left untouched.
- [x] Move `lastActivity` tracking to Redis, in the 3 files that actually enforce it (root `middleware/auth.js` is unused dead code, confirmed via grep for its requires — not worth touching)
- [x] Verified end-to-end: logged in as the seeded admin, called a protected endpoint, confirmed Redis key `last_activity:<userId>` created with ~1800s TTL; then manually set a 31-minutes-stale timestamp and confirmed the middleware correctly returns 401 "Session expired due to inactivity" — genuine sliding window confirmed both ways
- [x] Refresh-token flow (`POST /auth/refresh-token`) confirmed compatible without changes — it's a standalone endpoint (not behind `authenticateToken`), and a freshly refreshed token's `iat` naturally becomes the new Redis baseline on the next authenticated call
- [x] Frontend `apiClient.ts`'s 401 → refresh flow reviewed — already correctly excludes auth endpoints from the retry loop, reads the refresh token from storage, and dispatches `session-expired` only on genuine refresh failure. No bug found, no change needed (this was the reactive design already; it's now correct because the backend timeout is finally real)
- [x] Built a generic `src/hooks/useDraftPersistence.ts` (localStorage-backed, debounced autosave + restore-on-mount + `clearDraft()`) and wired it into the 3 surfaces named above, as they exist today: the Chat prompt input (`pages/User/AIChat.tsx`), the Sales "Add Project" form (`components/ninja-sales/AddProjectModal.tsx`, all 16 fields via one JSON-serialized draft), and the Website Builder "Create Website" modal (`components/web-builder/CreateWebsiteModal.tsx`, name + description). Each clears its draft on successful submit. Website Builder's modal will likely be replaced by Phase 3's wizard rebuild — the hook carries forward regardless, this just means today's surface isn't left with the known gap in the meantime.
- [x] **Real regression found and fixed post-verification**: caught via a live `npm run dev` restart — `api-gateway`'s Redis client connects lazily (`app.listen()` doesn't wait for it), so there's a ~1-2s window right after a fresh restart where an already-open, already-logged-in browser tab's requests hit the auth middleware before Redis is ready. The original fix's fallback (`user.lastActivity` / `iat` from the JWT, i.e. login time) doesn't know about ongoing activity that Redis was correctly tracking — so during that narrow window, a user who'd been logged in a while but continuously active could be spuriously rejected as "expired." The codebase's own existing convention (`checkTokenBlacklist`) is to fail OPEN when Redis is down; this fix didn't follow it. Fixed: `getLastActivity`/`updateLastActivity` in all 3 `redisClient.js` files now let Redis errors propagate instead of swallowing them into `null`/`false`, and all 3 middlewares wrap the check in `try/catch`, failing open (allowing the request through) on any Redis error rather than falling back to a stale timestamp. Verified: an isolated `getLastActivity` call against an unreachable Redis port genuinely throws (confirming the propagation), and the normal path (Redis reachable) still correctly enforces both the happy path (200) and genuine 31-minute staleness (401) exactly as before.

## Phase 3 — Website Builder rebuild `[BE+FE]` ✅ complete, verified live in browser (`feedback.md` §4 — "the largest single UI rework in the list")
